# Baseline: F# against Rust and Rails on the whole app (plan step 5b), 2026-10-06

`bench/run --apps reference,rust,fsharp,rust-identity,fsharp-identity --reps 3`, then `bench/breakdown` for where F#
spends a request. Nothing in `src/` changed: repo HEAD `dd5ae60` (the F# image is `campfire-fsharp:app` built from it).
Raw data, one JSON per app and rep, is in [`baseline-20261006/`](baseline-20261006/); `report.md` there is
`bench/report`'s full output (every metric, every concurrency); the breakdown's raw data and tables are in
[`baseline-20261006/breakdown*/`](baseline-20261006/breakdown/report.md).

**Where F# stands.** On the four read workloads at 16 connections F# serves 0.68–0.79× Rust's requests per second
(room page 0.75, messages page 0.79, sidebar 0.68, search 0.75), and 0.53–0.71× at one connection. Posting a message is
level at 16 connections (1.02×), 0.90× at 64 and 0.70× at one. Against Rails F# is 20–92× at 16 connections (Rust
20–124×). So the "faster than Rust on all five" aim is open on four of five, and the gap has named causes below: nearly
all of it is database access around SQLite's engine, the CLR's allocation and GC cost, HMAC for signed cookies, the
console logger and thread-pool spinning. The Falco layer is not one of them: it costs about 29 ns a request.

## Validity

Every number above was checked against the following, all in the per-run JSON and printed by `bench/report` (`report.md`):

- **Status of every response.** 116,216,645 responses over the 15 runs' HTTP suites: every one was 200 (no 3xx, 4xx or 5xx),
  zero connection errors, for every app, route and concurrency.
- **Rows written by "post a message".** The harness counts the messages of the write room in the app's own SQLite file before and
  after every run (warm-up included) and compares with the answers below 400: 0 mismatches in all 60 phases.
  Rails 20,239 posts / 20,239 rows; Rust 394,621 / 394,621; F# 327,409 / 327,409; Rust identity 413,454 / 413,454; F# identity
  354,072 / 354,072.
- **Response bytes per app per route** (one request each, gzip and identity, before any load; `report.md` has the full table):

  | Route | decoded bytes: Rails / Rust / F# | gzip on the wire: Rails / Rust / F# | c=16 average on the wire: Rust / F# |
  |---|---|---|---|
  | room page | 463,708 / 416,122 / 416,122 | 44,379 / 24,231 / 24,080 | 24,231 / 24,080 |
  | messages page | 430,925 / 383,844 / 383,844 | 34,855 / 16,158 / 15,967 | 16,158 / 15,967 |
  | sidebar | 31,427 / 30,763 / 30,763 | 6,268 / 5,910 / 5,910 | 5,910 / 5,910 |
  | search | 165,519 / 149,623 / 149,623 | 17,549 / 9,766 / 9,713 | 9,766 / 9,713 |
  | avatar, CSS, `/up` | 3,364, 1,218, 73 in all three | within 2 bytes | equal |
  | post a message (answer) | – | – | 1,992 / 1,992 (Rails 2,001) |

  F# and Rust send the same decoded bytes on every route, so they do the same work. F#'s gzip is 0.5–1.2% smaller on the
  three big pages (a different deflate implementation, the same decoded body): that is not a win and it is not a cost, only
  a note. The Rails pages are 11% bigger than Rust's and F#'s (a known Rust difference), so the F#-over-Rails and
  Rust-over-Rails ratios compare different bytes.
- **Load average before each run:** 1.31–1.45 (the harness's threshold is 1.5) for 13 of 15 runs; Rails rep 1 started at 0.53
  and Rust rep 3 at 0.06 (see the incident below). After a run it stands at 3.5–8.2. All values are in `report.md`.
- **Pinning:** `docker inspect` shows the cpuset; the generator's `taskset`; container memory sampled every 200 ms for the peaks.
- **Load generator headroom** (`bench/breakdown cpu` records its CPU next to the server's): on the page routes at c=16 it uses
  0.7–0.9 of its four cores, so the server is the limit (3.3–3.7 of four cores busy). On the cheap routes (avatar, CSS, `/up`)
  it uses 1.1–2.0 cores at 80–150k req/s, and 3.55 of four for F#'s avatar at 190k req/s with logging off: those routes are close
  to what the generator can drive, which is why they are not used to claim anything.
- **Outliers.** F#'s post-a-message run at c=64 in rep 2 gave 2,802 req/s (max latency 1.4 s) against 5,400 and 5,321 in the
  other two; the median is used. It did not come back in 8 further isolated runs of F# (4.8–6.4k req/s, max 30–132 ms),
  and Rust produced the same kind of stall in 2 of its 8 isolated runs (a 594 ms max and a 1,121 ms max with 4,065 req/s)
  and in its own rep 2 (585 ms max). The stalls are the WAL checkpoint and host I/O, not something F# does alone.
- **What went wrong on the way, and what was done:**
  1. `bench/breakdown`'s first POST measurements at c=16 were single-connection: the sign-in page has no CSRF token, the
     empty `--csrf` argument vanished in word splitting and swallowed `--conc`. It was caught because Rust's and F#'s c=16
     POST throughput equalled their c=1; fixed (arrays), every POST number in the breakdown is after the fix. `bench/run`
     builds its arguments as arrays and was never affected.
  2. The apps log a line per request (as Thruster does), about 880 bytes for Rust and 340 for F#, into Docker's json log:
     9 GB for one Rust run. The Mac's disk filled between two runs (rep 3 of Rust was lost mid-run and rerun; nothing else
     was affected) and the VM had to be restarted (04:27), so Rust rep 3 started on a cold VM (load 0.06). `fstrim` between
     calls since. The log line's CPU cost is measured below (`LOG_REQUESTS=false` in a sensitivity run).
  3. A throwaway `bench/falco` benchmark and `perf`-based profiling needed `linux-tools-6.8.0-117-generic` in the VM
     (installed with apt; `kernel.perf_event_paranoid=-1` set while profiling).
- **Known limits.** One VM on a laptop, three reps; spreads are small (±1–3%) except the stalls above. The Rust perf figures
  are from the stripped-of-callchain symbols the Rust image has (see the breakdown's caveats). Docker's log driver and the
  kernel's loopback work run outside the cpusets.

## Where a request's time goes

Four independent measurements, each answering a different question:

1. **CPU per request, unprofiled** (`bench/breakdown cpu`, 3 reps): the container's cgroup `cpu.stat` over a run, divided by the
   requests, next to the load generator's CPU. This is the number the other two scale to.
2. **perf of the app's process** (`bench/breakdown perf`, c=16): `perf record -g` at 999 Hz, with the CLR's perf map for
   managed names. A sample is a millisecond of CPU. F# call chains are complete (frame pointers survive the P/Invoke into
   SQLite, the kernel and the CLR), so each sample goes to the layer owning the nearest frame; Rust's chains stop at the first
   Rust frame, so its samples go to the first crate or C library named on what chain there is (libc, kernel and allocator
   time under a Rust frame is shown as libc/kernel/allocator rather than as its caller). perf costs 3–14% (F# room page 179 µs
   under perf, 174 unprofiled; Rust 139 against 122), and the Rust runs vary more under it than F#'s do, so the Rust
   decomposition is good to a few µs per row, not to the decimal.
3. **dotnet-trace thread-state profile** (`bench/breakdown profile`, F#): every managed thread's stack at a fixed interval, with
   `dotnet-counters` for GC and allocation. It shows where threads wait (locks, GC suspension), which perf's CPU view cannot.
4. **Micro-benchmark of the routing layer** (`bench/falco`): Falco and routing alone, in process.

### What the Falco layer costs

Plainly: **about 29 nanoseconds per request, and no allocation.** The app's pipeline ends `UseRouting`, `UseFalco [ any "/cable"
… ]`, `UseFalcoNotFound dispatch`: Falco routes `/cable` and nothing else, and every other request, all five workloads
included, falls through its endpoint match to the terminal handler that calls the kit's dispatch, where the Rails route table
(the kit's own matching, `RouteTable.dispatch`, 0.5–3.3 µs) picks the controller. `bench/falco` times that tail on a
`DefaultHttpContext`, in process, pinned to one CPU, 3 million requests per variant, 7 interleaved rounds, medians:

| Pipeline tail | ns/request | over a bare terminal handler | bytes allocated |
|---|---|---|---|
| terminal handler only (`app.Run`) | 3.5 | – | 0 |
| hand-rolled path check for `/cable`, else the handler | 10.2 | +6.7 | 0 |
| `UseFalcoNotFound` only | 6.0 | +2.5 | 0 |
| `UseRouting` + terminal handler | 30.7 | +27.2 | 0 |
| **the app's tail, request for any other path** | **32.7** | **+29.1** | 0 |
| the app's tail, request for `/cable` (a Falco endpoint) | 32.7 | +29.2 | 0 |
| every one of the 177 Rails routes as a Falco endpoint, request matches none | 43.5 | +39.9 | 0 |
| the same, request matches the last route | 32.6 | +29.1 | 0 |

That is 0.1% of a `/up` request (27 µs) and 0.015% of a sidebar request (199 µs). The thread-state profile agrees: the
frames of `Falco` and `Microsoft.AspNetCore.Routing` own 0.0% of the samples on every route (1–5 ms of 36 s on the sidebar), and
perf gives "Falco and routing" 0.0 µs. Registering all 177 routes with Falco would add 11 ns. There is no Falco cost to
recover; the routing layer is not a target.

### What the request log line costs

Both apps write one line per request (Thruster's behaviour, kept). With `LOG_REQUESTS=false` in both (one rep, c=16, CPU per
request): F# 173.8 → 156.3 µs on the room page (-10%), 199.2 → 171.5 on the sidebar (-14%), 188.5 → 162.7 on search (-14%),
545.9 → 504.5 on a post (-8%), `/up` 28.2 → 20.0 (-29%), CSS file 20.8 → 16.7 (-20%), avatar 22.1 → 18.2 (-18%); Rust
122.2 → 104.5 (-14%), 123.8 → 104.1, 125.4 → 109.1, 381.4 → 353.1, `/up` 23.0 → 18.1 (-21%), CSS 15.1 → 10.8 (-28%). So the
line costs both ports 7–29%, F# a little more on the cheap routes: the console logger formats through `ILogger`, queues
the line under a monitor (the `FrontResponse.Finish` contention above) and flushes a `StreamWriter` per line on a
`Console logger` thread that takes 2.4% of the CPU on a page and 10.9% on `/up`.

### Thread-pool spinning at low concurrency

At c=1 F# spends 42–56% of its CPU in `LowLevelLifoSemaphore.Wait` (spinning, `sched_yield`, futex wake-ups) because idle
pool workers spin before parking; that is why a lone client costs 3–4× Rust's CPU. As an experiment, not a change, one rep
with `DOTNET_ThreadPool_UnfairSemaphoreSpinLimit=0` (F# only, same machine):

| | CPU µs/req default → spin 0 | req/s default → spin 0 |
|---|---|---|
| room page, c=1 | 538 → 325 | 3,323 → 3,520 |
| sidebar, c=1 | 465 → 256 | 3,684 → 3,942 |
| `/up`, c=1 | 153 → 76 | 10,711 → 10,960 |
| post, c=1 | 1,024 → 644 | 1,916 → 1,989 |
| room page, c=16 | 174 → 176 | 21,503 → 20,265 (noise) |
| sidebar, c=16 | 199 → 204 | 18,653 → 17,846 (noise) |
| `/up`, c=16 | 28.2 → 23.5 | 78,258 → 82,737 |
| post, c=16 | 546 → 518 | 6,255 → 6,152 |

Halves the idle burn at one connection with no latency cost, neutral on the pages at 16. One more experiment,
`DOTNET_GCgen0size=4000000` (64 MB gen0 budget, one rep): room page 174 → 164 µs, sidebar 199 → 189, `/up` and post unchanged.

### Identity bodies

At c=16 with `Accept-Encoding: identity`, Rust spends 171 µs on the room page (gzip: 122) and F# 263 (gzip: 174): F#'s user time
rises 55 µs for the 416 KB body, Rust's 8 µs, while kernel time rises equally. The thread-state profile puts it in
`SocketPal.SysSend` and `Interop.Sys.SendMessage` (25% of F#'s CPU on that route against 14% in the gzip profile): Kestrel
copies the body into 4 KB pooled blocks and sends it as a `sendmsg` with many buffers.

## Ranked targets

Each gain is estimated from the tables above (CPU µs per request at c=16, scaled to requests per second at the 3.7 busy cores),
not prototyped, except where an experiment is cited. Together the first six are enough to reach Rust's CPU per request on the page
routes; beating Rust needs the DB wrapper and the runtime costs below Rust's, not merely level with it.

| # | Target | Evidence | Estimated gain |
|---|---|---|---|
| 1 | **Database access around SQLite's engine**: `Microsoft.Data.Sqlite`'s `SqliteDataReader`/`SqliteDataRecord`, the per-column P/Invoke stubs with `SafeHandle` add-ref/release, `sqlite3_bind_parameter_index` by name on every bind, row mapping, the reader pool's lock and the thread hand-off for each read | 37.0 µs against Rust's 8.0 (room page), 30.5/8.1, 33.9/5.7, 30.1/5.8, post 76.5/17.6; lock contention is `ReadQueue.TakeConnection` first | -25 to -29 µs per page request (-15% CPU, **+17% req/s** on the four read pages), -59 µs per post |
| 2 | **SQLite's engine runs more work per request** (more API calls, each taking the connection's mutex: `pthread_mutex_lock` 2.3–2.7% of CPU, `sqlite3_mutex_enter/leave` and the `.plt` stubs 1–2%). Open the connections `SQLITE_OPEN_NOMUTEX` as rusqlite does, one thread at a time per pooled connection is already guaranteed; fetch columns without re-entering the API per column | engine by owner 68.6 µs against 42.6 (sidebar), 91.8 against 54.7 (search), 216.5 against 186.5 (post), level on the room and messages pages; the engine's own instructions are 1.5–2× Rust's on all four read pages (25.1/16.7, 26.3/17.5, 32.0/17.9, 38.8/20.0) | -8 to -25 µs on sidebar, search and post (-4 to -12% CPU) |
| 3 | **Allocation volume and the CLR's runtime cost**: 100–161 KB allocated per page request (237 KB per post), GC pauses 4–7% of wall time, 90–215 gen0 collections a second, the server-GC threads 6–7% of CPU and the CLR's native runtime (allocation helpers, type checks, thread statics, stubs) 25–33 µs against Rust's allocator at 6–9 µs. Pool response and render buffers, take the `task { }`/`Actions.Bind` state machines and `List.map` allocations off the hot path; try a bigger gen0 budget | CLR runtime by resource 29.2 µs (room), 31.6, 26.4, 32.6, 71.8 (post) against Rust's 7.0, 5.0, 7.3, 5.9, 12.6; the gen0 experiment alone gave -5% | -15 to -25 µs per page request (-10%); post -50 µs |
| 4 | **HMAC for signed cookies and tokens, and key derivation**: `KeyGenerator.GenerateKey` through a `ValueTuple`-keyed lookup per call, `HMACSHA1.HashData` through OpenSSL's EVP per call, one avatar token signed per user in the sidebar (`MessageVerifier.sign`) | 15.2 µs against 6.1 (room), 29.8 against 17.6 (sidebar), 11.3/4.0, 12.1/3.0; libcrypto is 10% of F#'s sidebar CPU | -9 to -12 µs per page request (-5%): cache derived keys and HMAC states, sign with ARM SHA intrinsics as Rust's `sha2` does |
| 5 | **The request log line**: console logger formatting, the queue's monitor and a flush per line | 5.5–6.3 µs a request on the cheap routes (20–24% of CPU), 7–9 µs on pages; `LOG_REQUESTS=false` takes 10–14% off F#'s page CPU and 18–29% off the cheap routes | -6 to -9 µs per page request (-4%), -5 µs per cheap request; a pre-formatted byte buffer written in batches keeps the line |
| 6 | **Thread-pool spin and hand-offs**: workers spin before parking (`UnfairSemaphoreSpinLimit`), 6–8 pool work items per page request | c=1 CPU 3–4× Rust's; experiment above: -40 to -50% CPU at c=1 with +4–6% req/s, `/up` at c=16 -17% CPU and +6% req/s | c=1 -40% CPU, +5% req/s; cheap routes +6%; the pages at c=16 unchanged. Inlining reads on the reader thread (target 1) also removes a hand-off per query |
| 7 | **post a message: the file watcher and `lstat`**: a `.NET File Watch` thread takes 3.8% of the CPU during posts and `lstat` calls under `FileStatus` another 1.8–2%; probably the default `WebApplication` builder's `appsettings.json` change watcher, which sees every database and file write under the content root (not yet confirmed) | thread shares in `perf-fsharp-post_message-c16.json`: `.NET File Watch` 3.8% | -5% of a post (-25 to -30 µs): build the host without file-watched configuration |
| 8 | **Rich text on a post** (`Campfire.RichText` 23.1 µs against Rust's 10.9) | perf layers (the post's gzip is already cheaper in F#: 32.8 against 36.8) | -12 µs per post (-2%) |
| 9 | **Identity bodies through Kestrel**: 416 KB copied through 4 KB pooled blocks, `sendmsg` with many buffers | F# 263 µs against Rust 171 (room, c=16); 0.51× Rust at 64 connections | F# identity room page 14.4k → about 20k req/s; matters only to clients that don't accept gzip |
| 10 | **Fixed plumbing on the cheap path**: the HTTP plumbing group is 37.1 against 33.7 µs (room), 38.9 against 25.8 (sidebar), 40.7 against 27.9 (search), 18.2 against 10.7 (CSS file), 20.0 against 11.0 (avatar); `Guid.NewGuid` for the request id makes a `getrandom` call per request (1.5% of `/up`) | CSS file 24.1 against 15.1, avatar 26.6 against 15.2 under perf | -2 to -4 µs per request |
| – | **Cable fan-out and memory** (outside this step's tables, listed because they are gates): 0.56–0.72× Rust's messages a second, 4.5× its memory at 1,000 clients, peak memory 1.8× | "Other suites" | see `bench/results/cable-fanout.md` |

Item 1 plus item 2 is the largest block (a third of F#'s page CPU is SQLite's engine and the layers around it, against 29–38% in
Rust where the engine alone does it). Items 3–6 are each worth about 4–10% and are independent of it.

## Reproducing

All from the repo root; the colima VM runs the harness (`colima ssh -- bash -c 'cd … && …'`), `SERVER_CPUS=0-3 LOADGEN_CPUS=4-7
WORK=/var/tmp/campfire-bench-work`:

```sh
# the matrix, one unit per call (--only APP:REP; the alternating order comes from --apps and --reps)
bench/run --apps reference,rust,fsharp,rust-identity,fsharp-identity --reps 3 --only fsharp:2 --out bench/results/baseline-20261006
bench/report bench/results/baseline-20261006
# the breakdown
bench/breakdown cpu --reps 3                      # CPU per request, Rust and F# (add --identity, or LOG_REQUESTS=false in FSHARP_EXTRA_ENV and RUST_EXTRA_ENV)
bench/breakdown perf --apps fsharp,rust           # perf per layer (add --conc 1)
bench/breakdown profile                           # dotnet-trace thread-state profile and runtime counters, F#
bench/falco/run                                   # what Falco and routing cost, in process
bench/lib/breakdown_report.py DIR --perf DIR --nolog DIR --identity DIR
```

`bench/run` also gained the F# app (`FSHARP_IMAGE`, `FSHARP_EXTRA_ENV`), the build of the load generator in a container, the
cgroupfs cgroup path, tmpfs for the reference's `/rails/tmp` when not run as uid 1000, and `WORK`. The mid-run `docker logs`
volume (about 9 GB for one Rust run) needs `sudo fstrim -av` in the VM between calls.

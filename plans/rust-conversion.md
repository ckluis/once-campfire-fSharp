# Converting Campfire to Rust

Status: proposal (revised after Codex review, see the end)
Target repo: `basecamp/once-campfire-rust` (new)
Reference implementation: this repo, pinned by SHA as a submodule

## Goal

Ship a Rust implementation of Campfire that can't be told apart from the Rails app, on a support
matrix we define explicitly (below). Every screen in that matrix renders pixel for pixel the same,
every interaction behaves the same, and it's a drop-in replacement for existing ONCE installs. That
means the same SQLite database, storage directory, URLs, cookies and env vars. Nobody gets logged
out, and rollback to the Rails image works on data the Rust app has written.

The payoff is one application executable (plus libvips and ffmpeg as native dependencies) in place
of Ruby, Puma, Redis, Resque and Thruster. It should use less memory and have a smaller surface to
patch.

## Non-goals

- Redesigning anything. Any visual or behavioral difference is a bug until cutover, even ones that
  look like improvements. That includes adding server-side `client_message_id` dedupe, which Rails
  doesn't do today.
- Rewriting the frontend. The Stimulus controllers, Turbo, Lexxy, highlight.js and the CSS ship
  byte for byte.
- Supporting databases other than SQLite.

## What we're porting

| Layer | Size | Strategy |
|---|---|---|
| Ruby (models, controllers, helpers, jobs, channels, lib) | ~4,000 LOC | Rewrite |
| ERB/Jbuilder views | ~2,300 LOC, 89 files | Translate one file to one Askama template or JSON serializer |
| JavaScript | ~3,700 LOC | Copy verbatim |
| CSS | ~3,400 LOC, 26 files | Copy verbatim |
| Vendored JS (Turbo, Stimulus, Lexxy, Action Cable client, request.js, highlight.js) | — | Copy the built files out of the gems in the reference `Gemfile.lock` |

Those counts describe the application source, not the amount of Rails behavior we have to
reproduce. That behavior is the real work, and it's catalogued in the contracts below.

## Compatibility contracts

We port each contract against **golden vectors generated by the reference app** (Ruby scripts in
`reference-tools/`). We never port one from our reading of the docs. Where the contract is
security-relevant, we also assert the security property independently, because two implementations
can agree on something unsafe.

### Signing, encryption and CSRF
- **`session_token` signed cookie**: permanent, HttpOnly and SameSite=Lax
  (`app/controllers/concerns/authentication.rb`). The key comes from `secret_key_base` via PBKDF2,
  and the *signing digest is separate from the derivation digest* (Rails' cookie jar defaults
  it independently, and it may be SHA1). The golden vectors pin the iterations, key length, signing
  digest, envelope (`_rails` metadata with purpose and expiry), serializer and escaping. We verify
  every cookie Rails issued and issue cookies Rails accepts.
- **`_campfire_session`**: an encrypted cookie (AES-256-GCM) with a 20-year expiry
  (`config/initializers/session_store.rb`). It holds the CSRF secret and
  `return_to_after_authenticating`.
- **CSRF**: the full Rails rules. That means the CSRF secret kept separately from anything
  auth-related, masked tokens, per-form tokens where Rails emits them, the `authenticity_token`
  param, the `X-CSRF-Token` header, Origin checking, and the bot-key exemption
  (`protect_from_forgery … unless: bot_key?`). We test with **old browser tabs**: render a form on
  Rails, submit it to Rust, and the other way around.
- **Signed IDs**: `avatar` (no expiry) and `transfer` (4-hour expiry,
  `app/models/user/transferable.rb`).
- **Turbo signed stream names**: `Turbo.signed_stream_verifier_key` is derived from
  `secret_key_base` using `"turbo/signed_stream_verifier_key"` as the salt.
- **SGIDs in stored rich text**, plus the deliberate fallback in
  `lib/rails_ext/action_text_attachables.rb`. It accepts **invalid signatures for User attachments
  only**, including extracting from Rails 7 Marshal-era payloads. We port it exactly, restricted to
  User, and write a test that a tampered SGID for any other model is rejected.

### Persisted data (read by Rails after rollback)
- **STI class names** (`Rooms::Open`, `Rooms::Closed`, `Rooms::Direct`), the integer enums
  (`role`, `status`), the `involvement` strings, and the polymorphic `record_type` values
  (`Message`, `User`, `Account`, `ActionText::RichText`).
- **Timestamp format and precision** as Rails writes them to SQLite, and JSON columns
  (`accounts.settings`, blob `metadata`).
- **Active Record callback side effects**, which have to happen in the same order and the same
  transactions as in Rails:
  - message create touches the room, updates unread memberships, pushes, runs bot webhooks, and
    writes the FTS index after commit
  - boost create and destroy touch the message
  - membership destroy disconnects that user's sockets with reconnect
  - user creation grants memberships to every open room
  - deactivating or banning a user destroys their sessions and disconnects their sockets
- **SQLite settings**: immediate transactions, a 5-second busy timeout, foreign keys, and WAL, all
  per `config/database.yml`. We keep writing `schema_migrations` and `ar_internal_metadata`.

### Active Storage
- The frontend uploads **multipart XHR straight to `MessagesController`** (`models/file_uploader.js`).
  It doesn't use direct uploads. Lexxy attachments are limited to mentions and opengraph embeds
  (`rooms/show/_composer.html.erb`).
- The `/rails/active_storage/*` endpoints still ship, because stored URLs and external clients can
  depend on them. That covers blob and representation redirects and proxies, `direct_uploads` and
  the disk `PUT`. The latter two require authentication
  (`config/initializers/active_storage_authentication.rb`), while **downloads stay public behind
  signed URLs**, as tested in `test/controllers/active_storage_authentication_test.rb`. We also
  handle range requests, content disposition and checksum validation.
- **Variants**: `variation_digest` is a digest (SHA1) of a *Ruby Marshal dump* of the
  transformation hash. We implement the tiny Marshal subset needed (symbols, arrays, integers,
  hashes) and verify it against golden vectors for every variant the app defines (`:thumb`, the
  avatar `:square`, and the video poster's `resize_to_limit` preview). Existing
  `variant_records` and preview-image attachments have to be reused, not regenerated.
- The disk layout is `storage/files/ab/cd/<key>`, along with blob metadata analysis (dimensions,
  duration, `analyzed`, `identified`) and the libvips loader restrictions in
  `config/initializers/vips.rb`.

### Real time
- **The Action Cable protocol**: welcome, ping, confirm and reject, identifiers, `perform`, and
  `disconnect` with a `reconnect` flag. That covers the seven app channels **plus**
  `Turbo::StreamsChannel` with Campfire's `RoomStreamsAreAuthorized` patch, which rejects guarded
  room-message streams so that a leaked signed stream name can't bypass membership
  (`app/channels/concerns/room_streams_are_authorized.rb`).
- **Revocation**: subscribe, revoke (remove the membership, deactivate or ban), attempt a delivery,
  reconnect and resubscribe. This runs as a named test for every channel, including the stock
  Turbo channel.

### HTTP clients: three distinct policies, never one shared client
- **Opengraph unfurling** (`app/models/opengraph/fetch.rb`): DNS resolved through the private
  network guard, a pinned IP, every redirect re-checked, and 5MB and 10-redirect caps.
- **Web Push** (`config/initializers/web_push.rb`): endpoint restrictions and IP pinning.
- **Bot webhooks** (`app/models/webhook.rb`): *intentionally unrestricted*, because an admin
  configured them and they may point at internal services. They have a 7-second timeout and
  specific reply handling (text vs. attachment by content type).

### Request contracts
- Rails nested params across urlencoded, multipart and JSON bodies, and the `_method` override.
- Format negotiation for html, turbo_stream, json and svg, by extension and `Accept` header, plus
  Turbo Frame requests.
- The bot API accepts **raw request bodies** or top-level multipart attachments, returns
  pagination headers, and uses specific status and `Location` combinations
  (`app/controllers/messages/by_bots_controller.rb`).
- Message pagination is **custom**: timestamp-based, 40 per page, with `page_around` returning up
  to 81 messages (`app/models/message/pagination.rb`). `geared_pagination` is used only for users
  and autocomplete, where we match its `Link` and `X-Total-Count` headers.
- Search runs Unicode-aware query preprocessing before FTS5 (`searches_controller.rb`).
- Conditional GETs (ETag and 304), HEAD, the `X-Version` and `X-Rev` headers, proxy-derived host
  and remote IP, and cookie deletion.

### Packaging
- The env vars (`SECRET_KEY_BASE`, `VAPID_*`, `SSL_DOMAIN`, `DISABLE_SSL` and others), the `/up`
  health check, and the storage paths under `/rails/storage`.
- The `db:prepare` behavior at boot.
- The backup hook runs the **SQLite online backup API** against a live writer
  (`script/admin/prepare-backup`). Restore drops the WAL and SHM files (`hooks/post-restore`).
- Both published CPU architectures.

## Framework decision

**Recommendation: Axum for HTTP plumbing, with a Rails-compatibility layer on top. Controllers
never touch Axum types.**

My first draft proposed going straight to `hyper` with an in-house router. Codex argued against
that, and the argument holds. Everything that makes Campfire hard (Rails params, cookies, CSRF,
format negotiation, URL helpers) is custom work under *either* approach. Going frameworkless only
adds ownership of the parts that aren't hard but are easy to get subtly wrong: routing edge cases,
body limits, request cancellation, slow clients, WebSocket upgrades, graceful shutdown and file
streaming. Axum is a thin layer over hyper and tower and doesn't impose a lifecycle.

How we use it:

- **Axum's `Router`** is used only for dispatch and WebSocket upgrades. Every route maps to one
  adapter that builds our `Ctx` (request, params, cookies, session, current user, flash, format,
  clock) and calls a plain `async fn action(c: &mut Ctx) -> Result<Response>`.
- **Before-action chains are explicit, ordered function calls** in each controller, with early
  return, mirroring the Rails declaration order: `set_current_request`, `block_banned_requests`,
  `require_authentication`, `deny_bots`, `verify_csrf`, `set_room` and so on. We don't use tower
  middleware for these, because stacking middleware doesn't reproduce Rails' `only:` and `except:`
  semantics or the skip rules.
- **We don't use Axum extractors** beyond the adapter. That keeps controller code independent of
  Axum, so swapping the plumbing later is cheap.

We rejected the other options:
- **Actix Web**: capable, but it offers nothing over Axum for this app, and the tokio ecosystem
  alignment (tungstenite, reqwest, rustls) is better with Axum.
- **Loco, Rocket and Poem**: their opinions about ORM, auth, sessions and jobs conflict with the
  "same database, same cookies, same URLs" requirement.
- **Raw hyper**: covered above. It means more ownership without any compatibility benefit.

Phase 0 validates this with the vertical slice below before we commit. If the slice turns up a
concrete obstruction in Axum, we revisit the decision then, with evidence.

## Crates

| Concern | Choice | Notes |
|---|---|---|
| HTTP | `axum`, `hyper`, `tokio` | See above. The front server in kit enforces body limits and timeouts (MAX_REQUEST_BODY, HTTP_READ/WRITE_TIMEOUT) |
| WebSockets | Our own upgrade and framing over hyper (`cable/src/socket.rs`) | Action Cable protocol implemented in `cable/` |
| Database | `rusqlite`, bundled SQLite with FTS5 | One writer task that owns the write connection and takes a bounded queue of work, plus a reader pool. We chose it for simplicity and transparency. (SQLx's offline mode does exist, so we aren't avoiding it for build-time reasons.) |
| Templates | `askama` | One template per ERB file at the same relative path. We port `content_for`, `form_with`, `link_to`/`button_to`, `image_tag`, `turbo_frame_tag`, polymorphic paths and `SafeString` escaping as a helpers module, each one tested against golden output from the reference app's helpers. |
| JSON views | hand-written `serde` serializers | One per Jbuilder file, diffed against Rails' output |
| Rich text | `html5ever` plus our own sanitizer walker, or `ammonia` if it can express all three layers | See Rich text below |
| Images | `libvips` over FFI | Pinned together with its codec libraries (libwebp, libjpeg-turbo, libpng, libheif) as an image package inventory. Orientation, metadata stripping and `Q` settings match ruby-vips' defaults. |
| Video posters | `ffmpeg` subprocess | The same argv as Active Storage's `VideoPreviewer` |
| Passwords | `bcrypt` | `$2a$` cost preserved |
| Web Push | `web-push` crate, or a port of `lib/web_push` | Verify VAPID key encoding, expiry, removal of invalid subscriptions (410/404), timeouts and IP pinning |
| QR codes | `qrcode` | Pin the version, error-correction level, mask and SVG geometry to RQRCode's output from `qr_code_controller.rb`. Any valid QR code isn't good enough, because the pixels have to match. |
| Time | `jiff`, with a `Clock` trait | Injected at the *service* boundary (models, jobs, presence, token expiry), not just into `Ctx` |
| Crypto | `hmac`, `sha1`, `sha2`, `pbkdf2`, `aes-gcm`, `base64` | Rails MessageVerifier and MessageEncryptor |

**Jobs and pub/sub (Redis, Resque and Puma cluster go away):**
- **Jobs.** Today, Resque runs as its own process against a non-persistent Redis
  (`config/redis.conf`). Queued work survives a worker crash but not a Redis restart. None of the
  jobs retry (`retry_on` is commented out in `application_job.rb`). The replacement is an
  in-process runner that enqueues *after commit*, uses a **bounded** queue (it rejects or logs
  when full rather than growing memory without limit), bounds concurrency per job type, and drains
  on graceful shutdown with a deadline. This does change the failure boundary: a process crash now
  loses queued work that a separate Resque process would have kept. We accept that deliberately,
  because a webhook, a push or banned-content cleanup is best-effort today anyway. If that proves
  wrong, the fix is a SQLite `jobs` table.
- **Pub/sub.** We use in-process `tokio::broadcast`, one channel per stream. A slow receiver that
  **lags gets disconnected with `reconnect: true`**. It doesn't silently skip messages. On
  reconnect, the client's existing `refresh_room_controller.js` path fetches new and updated
  messages. That path doesn't recover deletions or authorization changes, so we test it
  specifically. If the gap is real, Rails has the same gap on a Redis blip, and we document it
  instead of inventing new behavior.

## Rich text

This is the highest-risk area for security, so it gets its own spike in Phase 0.

- Port the three layers exactly as written in `app/helpers/content_filters/`:
  `RemoveSoloUnfurledLinkText`, then `SanitizeTags` (which removes disallowed elements
  *together with their contents*), then `SanitizeAttributes`, then Action Text's sanitizer (with
  `lib/rails_ext/action_text_allowed_tags.rb`), then the re-sanitization in `auto_link`. Each has
  its own allowlist. Opengraph embeds constrain URLs relative to the request host
  (`lib/rails_ext/actiontext_opengraph_embeds.rb`).
- **The edit path is half the contract.** `rich_text_helper.rb` rebuilds attachment content and
  content types so that Trix-era mentions and embeds survive a round trip through Lexxy. We test
  the whole cycle: stored body, display, edit, save, display again, plain-text extraction, the
  search index, and the webhook plain body with recipient mentions removed.
- Differential fuzzing against Rails, plus **independent security assertions** that don't depend
  on the oracle: no `script` elements, no `on*` attributes, no `javascript:` URLs, and no `style`
  outside the allowlist in any output.

## Phases: vertical slices

Hard sequential layers don't work here. The read path needs attachments, and readiness needs the
cable, so we build thin slices end to end, each with an explicitly scoped parity gate.

**Phase 0: harness and the risky slice**
1. Create `once-campfire-rust` with the reference as the submodule `reference/`, pinned by SHA.
2. Build the parity harness (Docker Compose): the Ruby reference **in production mode**, with CSRF,
   caching, and `show_exceptions` all on (unlike `config/environments/test.rb`), next to the Rust
   candidate, both on identical copies of a seeded database and storage directory.
3. Exit criterion 1: **Ruby-vs-Ruby captures are pixel-identical across two runs** for the whole
   inventory. If we can't make the oracle deterministic, nothing downstream means anything.
4. Generate every golden vector: cookies, session, CSRF, signed IDs, SGIDs, Turbo stream names,
   variation digests, params trees and helper output.
5. **Vertical slice**: an existing Rails cookie authenticates on Rust, the room renders, a
   multipart message upload creates the blob, variant and FTS row, an authorized broadcast reaches
   a second user, the stock Turbo channel rejects a guarded stream, and then **Rails boots on the
   database Rust just wrote** and edits, deletes and searches that message. This proves the
   framework choice, the database approach, the cable approach and rollback before we start
   building out.
6. A deployment spike: TLS and ACME in-process (reusing Thruster's existing certificate storage),
   both architectures, and online backup against a live writer.

**Phase 1: auth and account surface.** First run, sessions, transfers, joining, bans, profile,
avatars (both uploaded and the generated SVG), users, bots and custom styles.

**Phase 2: rooms and messages.** The sidebar, every room type, pagination and deep links, the full
rich text pipeline, every attachment presentation, boosts, and edit and delete.

**Phase 3: real time.** Every channel, presence and the heartbeat, typing, unread and read
fanout, revocation tests, and reconnect and lag behavior.

**Phase 4: integrations.** The bot API, webhooks, Web Push, unfurling, search and the
banned-content job.

**Phase 5: packaging and cutover.**
- The image with a pinned package inventory.
- Replacing Thruster is its own milestone. Until then, we can run the Rust binary behind Thruster
  unchanged.
- Soak test on **copies** of real production data, replaying recorded GET traffic against snapshot
  copies. We don't shadow live traffic, because GETs aren't side-effect free: session resume,
  cookie refresh, room visits and presence all write.
- Ship cutover as a normal ONCE update. We test both upgrade and rollback on real data before
  release.

## Testing plan

The Ruby app at the pinned SHA is the oracle. We don't hand-write expected output, except for
security properties, which we assert independently.

### What "pixel perfect" covers

"Pixel perfect on every screen" isn't provable in the abstract, so we make it concrete. The
**support matrix** is:

- **Engines**: Chromium, Firefox and WebKit at pinned Playwright builds. Each comparison is Ruby vs
  Rust *on the same engine*.
- **Viewports**: 1440×900, 1280×800, 834×1194 (touch), 390×844 (touch, mobile UA), plus one
  capture 1px either side of every CSS breakpoint found in `app/assets/stylesheets`.
- **Color scheme**: light and dark.
- **Roles**: admin, member, and member of someone else's room.
- **Custom styles**: none, and a fixture stylesheet that touches every CSS custom property in
  `colors.css`.

Outside the matrix, we cover things with a manual checklist on real devices (an iPhone with Safari
and the installed PWA, an Android phone with Chrome and the installed PWA, desktop Safari). That
covers the soft keyboard (`soft_keyboard_controller.js`), native media controls, share sheets,
push permission prompts and zoom. Engineers run it before cutover and when the relevant templates
change.

### Layer 1: pixels

**The screen inventory** (`parity/screens.yml`) lists states. Each state is a route plus a setup
script plus an optional interaction. It's organized as:

- **Unauthenticated**: first run, sign in (empty, with an error, from a banned IP), join (valid and
  invalid code), the transfer link (valid and expired), the incompatible browser page, 404 and 500.
- **Rooms**: an empty room, a busy room, a direct room, a closed room, a room as a non-member, the
  `@message` deep link, the top and bottom of pagination, and the `page_around` boundaries.
- **Messages**: plain, long, emoji-only, code with highlighting, table, `s`/`u`/`mark`, mention
  (valid, and with a Marshal-era SGID), `/play` sound, opengraph embed, solo unfurled link, image,
  video, generic file, from a bot, edited, and with boosts (none, one, many, yours).
- **Interactions**: the actions menu, boost picker, edit form, composer (with text, with an
  attachment preview, with an upload in progress), mention autocomplete (with results and empty),
  lightbox, phone sidebar, typing indicator (one and many), unread and read badges, flash notice
  and alert, and PWA install instructions for each platform.
- **Settings**: the account page (admin and member), users, bots, custom styles, new and edit for
  every room type, involvement, profile, push subscriptions, and search (empty, recent and results).
- **Real time**: two browser contexts per test, capturing B's view after A sends, edits, deletes,
  boosts, types, leaves, or is removed from the room.

**Determinism:**
- One pinned Docker image for both apps (Playwright, browsers, fonts, no GPU). We never capture on
  a host machine.
- A shared seed: a SQLite snapshot and storage directory generated once by the reference app from
  fixtures plus a scripted scenario, with absolute timestamps chosen to avoid ties.
- Frozen time *only in visual scenarios*. Ruby runs under libfaketime, Rust uses its `Clock`, and
  the browser uses `page.clock.setFixedTime`. Expiry, presence timeouts and ordering get
  advancing-clock scenarios in Layer 3.
- **Animations**: we don't disable animations globally, because that can change the state under
  test. For example, the flash removes itself on `animationend`, and fast-forwarding it erases the
  flash before capture. Instead the harness pauses every `document.getAnimations()` at a
  state-specific `currentTime` declared in the inventory (for example, the flash at 500ms). We
  hide the caret.
- **Readiness** is based on real signals, not the presence of attributes. A test-only script
  exposes the Stimulus application, so the harness waits until every `data-controller` element
  has a connected controller instance. It waits for every Action Cable subscription in
  `consumer.subscriptions` to be confirmed, not just `turbo-cable-stream-source[connected]`,
  because the presence, typing, read and unread subscriptions are made manually. It also waits
  for `document.fonts.ready`, network idle, and decoded images and video posters.

**Comparison**: we decode both PNGs to RGBA and compare buffers exactly. The fast path is a byte
compare of the buffers, and we use `pixelmatch` only to draw the diff image, with
`includeAA: true` and threshold 0, since its defaults forgive antialiasing. Failures publish the
expected, actual and diff images plus the DOM diff to an HTML report. `parity/allowlist.yml` holds
the exceptions, each with a reason and an owner, and it must be empty at cutover.

**Generated media**: thumbnails, avatars, video posters and QR SVGs from the same inputs have to be
byte-identical, which a separate CI job checks.

### Layer 2: DOM and accessibility

For every state:
- **The normalized server HTML.** We parse it with html5ever, sort attributes, collapse
  insignificant whitespace, and mask volatile values with *typed* placeholders:
  `«sgid:User#3»`, `«signed_id:avatar:User#3»` and `«csrf»`. A token for the wrong record still
  fails.
- **Timestamps aren't masked away.** They're decoded and compared as values relative to the seed
  clock, because `data-message-updated-at` and friends drive pagination and refresh on the client
  (`messages_helper.rb`).
- **The live DOM** after connecting (`body.outerHTML`), and the **accessibility tree** (Playwright
  `ariaSnapshot`).

### Layer 3: protocol and state

- **HTTP replay.** Scripted sessions run against both servers, and we diff the status, the relevant
  headers and the normalized body. This covers every route and verb from `rails routes`, with
  declared-but-unimplemented actions classified as expected 404s. It also covers every format,
  the auth edges (no cookie, expired session, bot key on a non-bot route, bad or missing CSRF, bad
  Origin, banned IP, non-admin), malformed params, method overrides, conditional GETs and HEAD,
  Turbo Frame requests and unsupported formats.
- **Cross-server continuity**: sign in on Rails and continue on Rust, render a form on one and
  submit it to the other, and hand a transfer link from one server to the other.
- **State differential.** After every mutating scenario, we dump both databases (rows normalized
  for IDs and time), the attachment graph and the storage tree, and diff them. Then we **boot
  Rails on the Rust-written state** and run the reference system tests against it. This runs from
  Phase 0, not at the end.
- **Cable replay.** Raw WebSocket clients against both servers diff the frame sequences for every
  channel, including the stock Turbo channel, the revocation sequences, heartbeat and presence
  refresh, and the lag-disconnect path.
- **Advancing-clock scenarios**: transfer link expiry, presence connection timeouts, the
  `last_active_at` refresh and FTS ordering under concurrency.
- **Chaos tests**: dropped and stalled sockets, a slow reader, killing the process mid-job, and a
  backup during writes.
- **Ported suites.** We port the controller, model and channel tests in `reference/test` to Rust.
  The five Capybara system tests become Playwright tests that run against both servers.
  Rails' test environment turns CSRF and caching off, so we also run the ported tests with them
  **on**.

### Layer 4: differential fuzzing

- **Rich text**: the corpus is every fixture body, Lexxy output for each toolbar feature, Trix-era
  bodies, the OWASP XSS cheat sheet, malformed nesting, huge inputs, Unicode edge cases, and SGIDs
  that are valid, expired, tampered, cross-purpose, Marshal-era and for other models. Any
  sanitizer disagreement or failed security assertion blocks the release.
- **Params**: generated nested bodies go through both parsers, and we diff the parsed trees.
- **Signing**: Ruby→Rust and Rust→Ruby round trips for every verifier and encryptor, including
  expired and wrong-purpose tokens.
- **Search**: random queries, including FTS syntax errors and mixed scripts, go through the full
  preprocessing and must return the same IDs or the same error behavior.

### Proving the gates work

- **Coverage.** The reference runs under Ruby `Coverage` with `eval: true, branches: true`, which
  covers compiled ERB, so we gate on template *branch* coverage by the inventory, not just which
  templates render. We check that cached fragments don't hide renders by also capturing with
  caching off. Every route shows up in the replay, every Stimulus controller *connects* in at
  least one state, and every channel is subscribed at least once.
- **Mutation checks.** A CI job plants known defects in the Rust build (a missing class, a swapped
  `aria-label`, an off-by-one page size, a dropped broadcast, a relaxed sanitizer rule) and asserts
  that each one fails at least one gate. A gate that misses a planted defect is broken.
- **Reference drift.** Bumping the pinned SHA re-captures the baselines, and the port has to catch
  up before that PR merges.

## Risks

| Risk | Mitigation |
|---|---|
| The sanitizer diverges from Loofah (a security issue) | Phase 0 spike, fuzzing, independent assertions, and a fallback to our own walker over html5ever |
| Signing details (digest, envelope, escaping) are wrong, and everyone is logged out | Golden vectors before any auth code, plus cross-server continuity tests |
| Rust writes data that Rails misreads after rollback | The state differential plus booting Rails on Rust data, starting in Phase 0 |
| libvips or codec output differs | Pin the package inventory and check byte identity in CI |
| The browser nondeterminism floor is above zero | The Ruby-vs-Ruby gate in Phase 0, animation pausing instead of disabling, and pinned engines |
| An authorization regression in cable (the stock Turbo channel, revocation) | Named security tests for each channel |
| A process crash loses jobs that Resque would have kept | Accepted and documented; a SQLite jobs table if needed |
| Replacing Thruster (TLS, ACME, caching and compression headers) | A separate milestone, running behind Thruster until it's done |
| Upstream Campfire keeps moving | The pinned submodule and baseline re-capture per bump |

## Decisions

The first review raised these, and DHH answered:

1. **No live cutover.** Moving an install from Rails to Rust is an offline upgrade step. That rules
   out live shadowing, and in-flight jobs don't need to survive the switch.
2. **Jobs are best-effort.** The in-process runner is fine, and losing a queued webhook or push on
   a crash is acceptable. We won't build a SQLite jobs table.
3. **Headers only need the same shape.** Protocol parity checks that the same headers are present
   with equivalent meaning (content type, location, cache intent, cookies set or cleared). It
   doesn't require byte-exact values. That applies to the Thruster replacement too.

4. **A lean parity gate.** The frontend is byte-identical and the browser build is pinned, so the
   port can only change pixels by sending different bytes. The primary gate is therefore
   server-output parity for every state: the HTML, the live DOM, the accessibility tree, every
   subresource (status, header shape, body hash) and the cable frames, all on one engine and one
   viewport. A thin pixel layer backs it up: Chromium on desktop and phone in light and dark, plus
   a smoke set of about 20 states on Firefox and WebKit. Self-parity runs once on that matrix. The
   full matrix is kept for a final pre-release check.

## Review log

We reviewed the first draft with Codex (`codex exec`, read-only, with the codebase available). Its
findings that changed this plan:

- **Factual fixes.** Uploads are multipart XHR to `MessagesController`, not direct uploads. Blob
  downloads are public signed URLs, and only uploads are authenticated. Message pagination is
  custom, not `geared_pagination`. There's no `client_message_id` dedupe. Redis being
  non-persistent doesn't mean in-process jobs lose nothing. Puma does run in cluster mode. "Static
  binary" isn't achievable alongside libvips and ffmpeg. SQLx does have an offline mode.
- **Signing.** The cookie signing digest is separate from the PBKDF2 digest (it may be SHA1). The
  Turbo string is a key-derivation salt. CSRF involves more than a masked token.
- **Security.** Codex added the `Turbo::StreamsChannel` guard, revocation tests, three separate
  HTTP client policies, the User-only invalid-SGID fallback, and independent sanitizer assertions.
- **Data.** It added the callback side effects, STI, enum and polymorphic values, and the state
  differential plus Rails-on-Rust-data from Phase 0.
- **Harness.** It pointed out that `pixelmatch` forgives antialiasing by default, that disabling
  animations breaks the flash, that attribute-presence readiness is insufficient, that timestamp
  masking hides ordering bugs, that template coverage isn't branch coverage, and that the
  reference must run in production mode. It also said the pixel guarantee needs an explicit
  support matrix and real-device checks.
- **Framework.** I switched from raw hyper to Axum plus a compatibility layer, because the hard
  parts are custom work either way.
- **Phasing.** I replaced the layered phases with vertical slices, starting with an end-to-end risk
  slice that includes rollback, and dropped live shadowing in favor of replay against snapshots.

## After parity: benchmark, then optimize

Once the parity suite is green with an empty allowlist:

1. **Benchmark both apps** on the same seed and hardware. Measure request latency (p50, p99) and
   throughput per route family, Action Cable fan-out (messages per second to N connected
   clients, end-to-end delivery latency), memory at idle and under load, cold start, upload and
   variant processing, and search. Reuse `reference/test/performance/chatter.js` for the load
   shape.
2. **Performance round** on the Rust app, guided by profiles (flamegraphs, allocation counts).
   Every optimization has to keep the full parity suite green.
